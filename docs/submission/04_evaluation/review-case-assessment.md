# Review case assessment

These assessments trace each patch against the current application and its documented requirements. The patch contexts do not all match the current checkout; compatibility/build issues are distinguished from behavior that follows if a patch is adapted. Planned production components described in ADR-001 are not treated as implemented application behavior.

| Case | Assessment from the trace |
|---|---|
| [case-01.diff](../../../ops/evals/cases/case-01.diff) | **Confirmed requirement gaps.** The bulk-approval use case requires a second approver for invoices over $1,000, but this calls the existing single-approver flow. It also accepts nullable `Ids` and iterates without checking for null. The documented use case also asks for a pre-confirmation summary and the ability to exclude invoices; neither appears here. See [UC-1](../../use-cases/UC-1-bulk-approval.md) and [ApprovalService.cs](../../../backend/src/InvoiceApp.Domain/ApprovalService.cs). |
| [case-02.diff](../../../ops/evals/cases/case-02.diff) | **Not compatible with this checkout; unsafe query construction if wired.** The current controller has no `_queries` service, and the app uses an in-memory repository rather than SQL. As written against the current source, this does not build; if connected to a SQL executor, interpolating both parameters into SQL would allow query injection. See [InvoicesController.cs](../../../backend/src/InvoiceApp.Api/Controllers/InvoicesController.cs), [IInvoiceRepository.cs](../../../backend/src/InvoiceApp.Domain/IInvoiceRepository.cs), and [ops/README.md](../../../ops/README.md). |
| [case-03.diff](../../../ops/evals/cases/case-03.diff) | **Behavior changes, but correctness is unestablished.** The patch changes rounding to truncate toward zero, including rounding the discount separately; for example, a $1 amount with a 0.6% discount can remain $1.00 instead of rounding the discounted total to $0.99. I found no stated rounding policy that establishes which result is required. The current calculator also has a different method/signature, so this patch does not map directly to it. See [DiscountCalculator.cs](../../../backend/src/InvoiceApp.Domain/DiscountCalculator.cs). |
| [case-04.diff](../../../ops/evals/cases/case-04.diff) | **No behavior defect established.** It consistently renames the repository field and constructor parameter. |
| [case-05.diff](../../../ops/evals/cases/case-05.diff) | **Confirmed authorization gap if adapted to this app.** The invoice controller has no class-wide role restriction; sign-in alone does not restrict a caller to Admin. The project convention says destructive actions are Admin-only, and the existing update endpoint applies that restriction. The exact patch also uses members not present in the current controller/repository (`Delete`, `_logger`, `CurrentUser`), so it would not build against this checkout as-is. See [InvoicesController.cs](../../../backend/src/InvoiceApp.Api/Controllers/InvoicesController.cs), [IInvoiceRepository.cs](../../../backend/src/InvoiceApp.Domain/IInvoiceRepository.cs), and [AGENTS.md](../../../AGENTS.md). |
| [case-06.diff](../../../ops/evals/cases/case-06.diff) | **No production-behavior defect.** These add tests for behavior the current test class already covers; the timestamp range check is an additional assertion. See [ApprovalServiceTests.cs](../../../backend/tests/InvoiceApp.Tests/ApprovalServiceTests.cs). |
| [case-07.diff](../../../ops/evals/cases/case-07.diff) | **A privacy defect is not established by the available requirements.** The log would include invoice fields such as customer name and amount, but I found no current-app rule forbidding those fields in logs. The exact patch also references `_logger` and `CurrentUser`, which are absent from the current controller, so it does not build against this checkout as-is. See [Invoice.cs](../../../backend/src/InvoiceApp.Domain/Invoice.cs) and [ApprovalsController.cs](../../../backend/src/InvoiceApp.Api/Controllers/ApprovalsController.cs). |
| [case-08.diff](../../../ops/evals/cases/case-08.diff) | **Confirmed concurrency risk in the patched implementation.** It replaces `ConcurrentDictionary` with an unsynchronized `Dictionary`; concurrent requests can race on reads/writes, and the duplicate check followed by insertion is not atomic. The repository is registered as a singleton. See [Program.cs](../../../backend/src/InvoiceApp.Api/Program.cs). |
| [case-09.diff](../../../ops/evals/cases/case-09.diff) | **The README's reset instruction is false for this app.** The invoice repository and sign-in sessions are separate in-memory singletons; signing out and in does not recreate invoice data. The “lost when the process stops” statement is consistent with the in-memory store. The logging-level change is not shown to violate a requirement, and the current `appsettings.json` already has that ASP.NET Core level set to `Warning`. See [Program.cs](../../../backend/src/InvoiceApp.Api/Program.cs), [SessionStore.cs](../../../backend/src/InvoiceApp.Api/Auth/SessionStore.cs), and [appsettings.json](../../../backend/src/InvoiceApp.Api/appsettings.json). |
| [case-10.diff](../../../ops/evals/cases/case-10.diff) | **Confirmed error-handling defect.** Returning HTTP 200 with `"completed"` for any otherwise-unhandled exception would tell clients a failed action succeeded, bypassing the existing error-to-status mapping. See [ApiControllerBase.cs](../../../backend/src/InvoiceApp.Api/Controllers/ApiControllerBase.cs). |
| [case-11.diff](../../../ops/evals/cases/case-11.diff) | **Confirmed state-transition defect.** Removing `EnsurePending(invoice)` from `Approve` permits a second approval request to succeed after the invoice is already approved. A concurrency test passes on the original implementation and fails on this patch with two successes. The test verifies repeated concurrent calls, although the removed guard also permits sequential repeat approvals. See [ApprovalService.cs](../../../backend/src/InvoiceApp.Domain/ApprovalService.cs). |
| [case-12.diff](../../../ops/evals/cases/case-12.diff) | **Clean refactoring.** The extracted `RecordDecision` helper assigns the same approver and timestamp in the same order for both approval and rejection. Existing `ApprovalServiceTests` pass against the patch. See [ApprovalService.cs](../../../backend/src/InvoiceApp.Domain/ApprovalService.cs). |

## Verification of added cases

- `case-11.diff` applies cleanly. Its concurrency regression test passed against the original implementation and failed against the patch because both approval calls succeeded.
- `case-12.diff` applies cleanly. All seven existing `ApprovalServiceTests` passed against the refactor.
